# AI Agent 接入方案与后续优化排序

> 制定时间：2026-11-08
> 距结题约 9–10 周
> 前提：用户明确要求「AI Agent 功能一定要加」
> 现状：中期检查后项目未改动，阶段一（并发锁 / 单测）尚未动工

---

## 一、结论先行

**优化从四个方面按序推进，但 AI Agent 会重排整个计划。**

| 顺序 | 方面 | 周期 | 为什么排这个位置 |
|---|---|---|---|
| 1 | **Service 层地基**（并发锁、单测） | 第 1 周 | Agent 是「新的入口」，它调用的是**同一批 Service 方法**。地基不牢，Agent 会把缺陷放大 |
| 2 | **AI Agent 主干**（Function Calling + 工具集 + SSE） | 第 2–4 周 | 本次唯一的技术亮点，投入最大，也是论文创新点所在 |
| 3 | **Agent 增强 + 预约闭环**（报修分诊、智能排期、签到爽约） | 第 5–7 周 | 让 Agent 有更多可调用的工具，同时补业务闭环 |
| 4 | **工程化与交付**（前端体积、Docker、论文、PPT） | 第 8–10 周 | 保演示、保答辩 |

### 一个必须做的取舍

**砍掉（或大幅压缩）「设备借用」模块，把时间给 AI Agent。**

原计划里设备借用是第 6–8 周的第二条业务线。现在两件事在时间上直接冲突，而它们的价值不对等：

- 设备借用 = 多一个 CRUD 模块，工作量不小，但论文里只能写「又实现了一个功能」
- AI Agent = 可以单独写一章「智能交互设计」，答辩时老师问「创新点是什么」有东西可答，演示也有冲击力

**两条主线都摊薄，不如一个亮点讲透。** 如果后面时间富余，设备借用可以作为「Agent 工具集的第 8 个工具」轻量回归，而不是一个完整模块。

### 与原有「智能排期推荐」不冲突

原计划推荐智能排期作为技术亮点。现在把它**降级为 Agent 的一个工具** `recommend_slots(...)`：评分函数照旧（人数、设备需求、历史使用率），只是由 Agent 在对话中按需调用，而不是单独做一个页面。这样算法照样能写进论文，还多了一层「为什么由 Agent 来调度」的设计说明。

## 二、Agent 的定位：做什么、不做什么

**不要做一个挂在角落的聊天机器人。** 那是硬塞 AI，答辩老师一眼看穿，且对系统没有任何增益。

定位应该是：**用自然语言驱动现有业务的一个新入口**，核心是 Function Calling（工具调用），不是文本生成。

### 该做的（四个高价值场景）

| 场景 | 用户输入示例 | Agent 做什么 |
|---|---|---|
| **自然语言预约** | 「帮我约明天下午 2 点到 4 点，做数据库实验，4 个人」 | 解析意图 → 查空闲实验室 → 冲突检测 → **生成待确认卡片** → 用户点确认后提交 |
| **智能排期推荐** | 「下周找个能坐 30 人、有投影的时段」 | 调用 `recommend_slots` 评分，返回 Top 3 时段及理由 |
| **报修智能分诊** | 「显微镜灯不亮，还有点糊味」 | 判断紧急程度、追问设备编号、生成规范报修单、提示安全事项 |
| **数据问答与周报** | 「这个月哪间实验室最忙？有几单没修完？」 | 查统计接口，把数字转成自然语言结论 |

### 不做的

| 不做 | 原因 |
|---|---|
| 实验室规章 RAG 知识库 | 要引向量库、要切片、要维护语料，工作量大且**答辩演示不稳定**（检索命中率不可控） |
| Agent 自动审批预约 | 风险高，且答辩极易被质疑「AI 出错谁负责」。改为「Agent 给建议 + 人点确认」 |
| 多 Agent 协作 / 复杂规划 | 课程项目讲不清，也没有真实需求支撑，纯粹炫技 |
| 让 Agent 直接读写数据库 | **绝对禁止**，见第四节 |

## 三、技术架构

```
用户自然语言
   │ SSE 流式
   ▼
AiAgentController  /api/agent/chat
   │
   ▼
AgentOrchestrator  ── 会话上下文（内存 Map，限 10 轮 / 单次会话）
   │  ① 组装 system prompt + tools schema + 历史消息
   ▼
LlmClient  ── RestClient → {base-url}/chat/completions
   │  ② 返回 tool_calls 或最终回复
   ▼
ToolDispatcher → ToolRegistry（工具白名单）
   │  ③ 调用现有 Service 方法（携 UserContext）
   │     工具结果回灌 messages，循环最多 4 轮
   ▼
SSE 推送前端：「识别意图」→「调用 xx 工具」→「结果」→「最终答复」
   │
   └─ 无 key / 超时 / 网络异常 ──► RuleFallback（正则+关键词）
                                    └─ 走同一套 Service，保证演示不断
```

**新增代码约 300–400 行，集中在 6 个类**：

| 类 | 职责 |
|---|---|
| `AiAgentController` | SSE 端点、会话 ID、限流 |
| `AgentOrchestrator` | 多轮 tool-call 循环（最多 4 轮，防死循环） |
| `LlmClient` | OpenAI 兼容协议封装，超时/重试/错误归一 |
| `ToolRegistry` | 工具定义（name / description / JSON Schema）与白名单 |
| `ToolDispatcher` | 参数校验 → 权限判定 → 调用 Service → 结果序列化 |
| `RuleFallback` | 断网兜底解析器 |

### 工具集（全部复用现有 Service，零新业务逻辑）

| 工具 | 底层方法 | 可用角色 | 写操作 |
|---|---|---|---|
| `list_available_labs` | `LabService` + `ReservationService.timeline` | 全部 | 否 |
| `recommend_slots` | 新增评分方法 | 全部 | 否 |
| `create_reservation` | `ReservationService.create` | 全部 | **是，需二次确认** |
| `query_my_reservations` | `ReservationService.myPage` | 全部 | 否 |
| `cancel_reservation` | `ReservationService.cancel` | 全部 | **是，需二次确认** |
| `report_fault` | `RepairService.create` | 全部 | **是，需二次确认** |
| `query_repair_status` | `RepairService` | 全部 | 否 |
| `dashboard_summary` | `StatsService` | 按角色 | 否 |

> 审批类工具（`approve_reservation`）**默认不注册**。可以先做出来但要显式开关，答辩时说明「刻意不开放写权限给模型」比「做了」更得分。

## 四、四个关键工程决策（答辩老师必问）

### 1. Agent 绝不绕过业务层

工具只能调用 **Service 方法**，绝不能注入 Mapper 直接写库。这样现有能力自动全部生效：

- 时间冲突校验
- 权限与角色拦截
- 状态机合法性
- 操作日志
- 参数校验

老师问「AI 会不会把别人的预约改了」，答案是：**Agent 没有独立的数据通道，它和用户点按钮走的是同一个方法，`UserContext` 里是谁就是谁。**

### 2. 写操作 Human-in-the-loop

所有写工具不直接执行，先返回一张**待确认卡片**（「将为你预约 A302，明天 14:00–16:00，确认？」），用户点确认才真正调用 Service。

好处：防模型幻觉、防提示注入、防误操作，而且演示时这一步的视觉反馈很直观。

### 3. 必须有断网兜底

答辩现场断网、Key 过期、模型超时，都会让纯 LLM 方案当场归零。**`RuleFallback` 是必做项，不是可选优化**：用正则 + 关键词解析「明天下午 2 点」「A302」「4 个人」，走同一套工具完成预约。

演示时主动断一次网，展示降级路径仍可用 —— 这比模型答得漂亮更能体现工程判断。

### 4. 密钥与防注入

- `LLM_API_KEY` 走**环境变量**，不写进 `application.yml`、不进 git、不进截图
- System prompt 明确声明：不得忽略角色约束、不得调用未注册工具、不得输出其他用户数据
- 工具层做白名单 + 参数强校验，不信任模型返回的任何字段
- 只把必要字段塞进 prompt，**不要整表导出**
- 对话日志脱敏，记录「调用了哪个工具、耗时、成功与否」即可，便于答辩展示调用轨迹

## 五、技术选型：推荐手写，不上框架

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **手写轻量 Agent**（推荐） | 零新依赖（`RestClient` 是 Spring 6.1 自带，Boot 3.3.5 已含）；tool-call 循环约 80 行，可逐行讲清；兜底/重试/权限完全可控；启动不引入额外自动配置 | 要自己处理流式解析与错误归一 | ✅ **选这个** |
| Spring AI 1.0 GA（`@Tool` / `FunctionToolCallback`） | 生态标准、代码更少、论文里「采用主流框架」好听 | 要引一整套 BOM 与自动配置，可能和现有 `JacksonConfig` 冲突；框架把循环藏起来了，答辩问「Agent 怎么工作的」只能答「框架帮我做的」 | 备选 |

**判断依据**：毕设评的是「你理解了什么」，不是「你调了什么库」。手写的 tool-call 循环能画成时序图讲三分钟，这是加分项；用框架反而把最值钱的部分变成黑盒。

**什么时候改选 Spring AI**：如果指导老师明确要求用主流框架，或后续要接 MCP / 向量库，再切，工具定义那层可以平滑迁移。

### 模型配置

选 **OpenAI 兼容协议**的模型（DeepSeek 官方 API `https://api.deepseek.com/v1`，或阿里云百炼 / 腾讯云 TokenHub 上的同类端点），理由：

- 中文理解好，Function Calling 支持完整
- 按量计费，课程项目全周期成本可忽略
- 换模型只改 `base-url` / `model` 两个配置项，方便现场切备用

`application.yml` 建议：

```yaml
lab:
  llm:
    enabled: true
    base-url: ${LLM_BASE_URL:https://api.deepseek.com/v1}
    api-key: ${LLM_API_KEY:}      # 留空即自动走 RuleFallback
    model: ${LLM_MODEL:deepseek-chat}
    timeout-seconds: 20
    max-tool-rounds: 4
```

> `api-key` 为空时**不报错、直接降级到规则兜底**，这条设计能让项目在任何机器上都能跑起来。

## 六、前端形态

右下角悬浮助手面板，三个要点：

1. **SSE 流式输出**，逐字显示，不要转圈等半天
2. **工具调用轨迹**可折叠展开（「调用 `list_available_labs` → 返回 3 间空闲」），这是「Agent」和「聊天框」的视觉分界线，答辩一定要展示
3. **写操作确认卡片**内嵌在对话流里，按钮直接点

技术上都用现有的 Element Plus + axios，SSE 用原生 `EventSource` 或 `fetch` + `ReadableStream`，无新依赖。

## 七、分周实施（剩余 9–10 周）

| 周次 | 任务 | 验收标准 |
|---|---|---|
| 第 1 周 | 并发锁（`FOR UPDATE` 锁实验室行）+ 15 个单测 + 压测脚本 | 20 并发抢同一时段只成功 1 条；`mvn test` 全绿 |
| 第 2 周 | `LlmClient` + `ToolRegistry` + `ToolDispatcher` 骨架，接 3 个只读工具 | Postman 调 `/api/agent/chat` 能返回工具结果 |
| 第 3 周 | 多轮循环 + SSE + 前端助手面板 | 「查空闲实验室」全链路可见调用轨迹 |
| 第 4 周 | 写操作工具 + 二次确认卡片 + `RuleFallback` | 断网 / 空 key 仍能完成预约；20 个提示注入用例全被拦截 |
| 第 5 周 | `recommend_slots` 评分函数 + 智能排期 | 推荐 Top 3 有理由说明，与真实空闲数据一致 |
| 第 6 周 | 报修分诊 + 数据问答周报 | 自然语言生成报修单、回答统计问题 |
| 第 7 周 | 签到爽约 + 信用分（可选，视进度） | 违约自动记分，限制预约生效 |
| 第 8 周 | 前端按需引入（2.8 MB → 约 1 MB）+ Docker Compose | `docker compose up` 一键起 |
| 第 9 周 | 论文新增章节、PPT 扩到 18–20 页 | 智能交互设计一章定稿 |
| 第 10 周 | 全流程演练 3 遍 + 10 个高频问答 | 断网演示、权限追问、成本追问都对答如流 |

**硬检查点**：第 4 周末若 `RuleFallback` 未跑通，**暂停 5–7 周的增强功能**，先把演示链路保住。

## 八、答辩演示脚本（约 3 分钟）

1. 学生账号登录，打开右下角助手
2. 输入「帮我约明天下午 2 点到 4 点，做数据库实验，4 个人」
3. 展示轨迹：识别意图 → `list_available_labs` → 发现 A302 时段冲突 → `recommend_slots` 推荐 B205
4. 点确认卡片 → 返回预约单号，切到「我的预约」页面验证真的写进库了
5. 输入「我那台显微镜灯不亮，还有糊味」→ Agent 追问设备编号 → 生成报修单，标为紧急
6. **拔掉网线 / 清空 key** → 再发一条预约 → 规则兜底照样完成，页面标注「离线模式」

第 6 步是全场最有说服力的一下。

## 九、答辩高频问题预备

| 问题 | 答法要点 |
|---|---|
| AI 会不会绕过权限改别人数据？ | Agent 无独立数据通道，全部走现有 Service，`UserContext` 决定身份；写操作还需人工二次确认 |
| 模型幻觉把参数填错了怎么办？ | 工具层做参数强校验；写操作不自动执行，先给确认卡片 |
| 断网了系统还能用吗？ | 有 `RuleFallback`，核心预约流程离线可走，演示可现场验证 |
| 为什么不用 Spring AI / LangChain？ | 需要能完整讲清 tool-call 循环，且不想引入与现有自动配置冲突的整套 BOM；协议层是标准的，后续可平滑迁移 |
| 提示注入怎么防？ | System prompt 约束 + 工具白名单 + 参数校验 + 写操作人工确认，四层 |
| 用了多少 token / 成本？ | 每次对话只带必要字段，日志里记录调用轨迹，按量计费，课程项目成本可忽略 |
| 这不就是个聊天框吗？ | 区别在于能**调用业务工具并产生真实写入**，轨迹面板可见，且落库结果可查 |
