## 一、当前基线

先把已有的东西说清楚，避免重复投入。

| 维度 | 现状 |
|---|---|
| 代码规模 | 后端 52 个 Java 文件 2825 行；前端 14 个 Vue 组件 4943 行 |
| 数据表 | 7 张（sys_user / lab / equipment / reservation / repair_order / repair_log / notice） |
| 接口 | 48 个 REST 接口，统一 `{code,msg,data}` 返回体 |
| 演示数据 | 36 用户、12 实验室、237 设备、384 预约、26 工单、102 条流转记录 |
| 测试 | `scripts/smoke_test.py` 33 项端到端断言（需先起服务） |
| 单测 | **无**（`src/test` 不存在） |
| 文档 | 需求与数据库设计文档（209 段 / 23 表 / 6 MB）、14 页答辩 PPT、5 分钟中期讲稿 |

**已验证无问题的点**（不要再花时间）：

- 前端路由已全部懒加载（`() => import()`）
- 列表关联字段已用 `selectBatchIds` 批量填充，**无 N+1 查询**

**已确认的真实缺陷**：

- `ReservationService.java:224-234` 的 `checkConflict()` 只做 `selectCount`，无锁。MySQL REPEATABLE READ 下并发请求可双通过
- `approve()` 的二次校验（L163）同样无锁，双审批人会都通过
- JWT 12 小时有效，改密码后旧 token 仍可用
- 无操作日志表，审批与状态变更无审计留痕

## 三、四阶段计划

### 阶段一：补地基（第 1–2 周）

目标：把已有功能做扎实，把中期检查里"承认的不足"全部消掉。

|---|---|---|---|
| 1.1 | 预约并发锁 | `ReservationService.create/approve` 开头加 `SELECT ... FOR UPDATE` 锁实验室行 | 并发脚本压测 20 个请求抢同一时段，只有 1 条成功 |
| 1.2 | 单元测试 | 新建 `src/test/java`（`spring-boot-starter-test` 依赖**已在 pom 中**，直接写测试类即可） | ≥ 15 个用例：时间重叠判定 6 个边界、状态机非法流转 5 个、密码校验 2 个 |
| 1.3 | 操作日志 | 新增 `sys_log` 表 + `@Log` 注解 + AOP 切面 | 审批、改设备状态、删用户都留痕，管理端可查 |
| 1.4 | Token 失效 | `sys_user` 加 `token_version`，签发写入 claim，拦截器比对 | 改密码后旧 token 立即 401 |

**阶段交付**：测试从 33 项扩到 48+ 项；PPT 第 14 页"不足"从 4 条减到 2 条。

## 四、技术亮点：三选一

毕设论文通常需要一处"有设计深度"的地方。三个候选，选一个做深，不要都碰。

| 候选 | 内容 | 论文可写 | 难度 |
|---|---|---|---|
| **A. 智能排期推荐** | 按人数、设备需求、历史使用率给实验室打分，推荐 3 个最优空闲时段 | 算法设计一章：评分函数、权重调参、效果对比 | 中高 |
| **B. 冲突检测的并发正确性** | 行锁 + 乐观锁双方案对比，压测数据支撑 | 一小节，但技术含量高，老师爱问 | 中 |
| **C. 信用分模型** | 违约扣分规则、恢复机制、阈值设定依据 | 可以写，但偏业务，创新性弱 | 低 |

**推荐 A**。理由：能真正给用户带来价值（学生不用自己翻日历找空档），有算法可以写，演示时"点一下给我推荐"很直观。B 作为阶段一的副产品自然就有了，不用额外投入。C 是阶段二的副产品。
