# 数据库设计说明

> 数据库：MySQL 8.0　字符集：utf8mb4　存储引擎：InnoDB
> 库名：`lab_system`　表数量：12
> 建表脚本：`lab-backend/src/main/resources/sql/schema.sql`
> 初始化数据：`lab-backend/src/main/resources/sql/data.sql`

---

## 一、设计原则

| 原则 | 说明 |
|------|------|
| 不建物理外键 | 关联关系由 Service 层校验保证。避免级联删除误伤数据，也便于后续分库或数据迁移 |
| 状态用字符串枚举 | `status` 用 `PENDING`/`APPROVED` 等可读值，而非 0/1/2。排查问题时直接看得懂，代价是少量存储空间 |
| 时间字段分离 | 日期用 `DATE`、时刻用 `TIME`、时间点用 `DATETIME`，不用字符串存时间，避免比较和时区歧义 |
| 单号独立唯一索引 | 预约单号、工单号、资产编号、实验室编号都建唯一索引，业务上防重复，也便于按单号直查 |
| 冗余字段不落库 | 列表展示需要的 `labName`、`equipmentName` 等在实体里用 `@TableField(exist = false)` 承载，查询时组装 |
| 索引按查询路径建 | 只给实际会用于 WHERE / ORDER BY 的字段建索引，避免写放大 |

## 二、表关系总览

```
                        ┌──────────────┐
                        │   sys_user   │  用户（四种角色）
                        └──────┬───────┘
              ┌────────────────┼────────────────┬──────────────┐
              │                │                │              │
        ┌─────▼─────┐   ┌──────▼──────┐  ┌──────▼──────┐ ┌─────▼──────┐
        │reservation│   │repair_order │  │credit_record│ │  message   │
        └─────┬─────┘   └──────┬──────┘  └─────────────┘ └────────────┘
              │                │
        ┌─────▼─────┐   ┌──────▼──────┐        ┌──────────────┐
        │    lab    │◄──┤  equipment  │        │ credit_appeal│
        └─────┬─────┘   └─────────────┘        └──────────────┘
              │                │
        ┌─────▼─────┐   ┌──────▼──────┐
        │lab_closure│   │ repair_log  │
        └───────────┘   └─────────────┘

        ┌──────────┐    ┌──────────┐
        │  notice  │    │ sys_log  │
        └──────────┘    └──────────┘
```

关系说明：

- `sys_user 1 ──< reservation >── 1 lab`：一个用户可有多条预约，一条预约对应一个实验室
- `sys_user 1 ──< repair_order >── 1 equipment >── 1 lab`：报修单关联设备，设备归属实验室
- `repair_order 1 ──< repair_log`：一个工单有多条流转记录
- `sys_user 1 ──< credit_record`：一个用户有多条信用变动
- `sys_user 1 ──< message`：一个用户有多条站内信
- `lab_closure.lab_id` 为空表示全校闭馆

## 三、表结构明细

### 3.1 sys_user — 系统用户

| 字段 | 类型 | 允许空 | 默认值 | 说明 |
|------|------|--------|--------|------|
| id | BIGINT | 否 | AUTO | 主键 |
| username | VARCHAR(50) | 否 | - | 登录账号，唯一 |
| password | VARCHAR(100) | 否 | - | BCrypt 密文，接口不返回 |
| real_name | VARCHAR(50) | 否 | - | 真实姓名 |
| role | VARCHAR(20) | 否 | - | ADMIN / TEACHER / STUDENT / REPAIRER |
| user_no | VARCHAR(30) | 是 | - | 学号或工号 |
| dept | VARCHAR(100) | 是 | - | 学院或部门 |
| phone | VARCHAR(20) | 是 | - | 联系电话 |
| email | VARCHAR(100) | 是 | - | 邮箱 |
| avatar | VARCHAR(255) | 是 | - | 头像地址 |
| status | TINYINT | 否 | 1 | 1 正常 / 0 停用 |
| token_version | INT | 否 | 0 | 令牌版本，改密或停用时自增 |
| credit_score | INT | 否 | 100 | 信用分 0–100，低于 60 禁止预约 |
| violation_count | INT | 否 | 0 | 累计爽约次数 |
| create_time | DATETIME | 是 | - | 创建时间（自动填充） |
| update_time | DATETIME | 是 | - | 更新时间（自动填充） |

**索引**：`uk_username(username)`、`idx_role(role)`

**设计要点**
- `password` 存 BCrypt 密文，长度 100 足够（BCrypt 输出 60 字符）。
- `token_version` 是 JWT 主动失效的关键：每次签发写入 JWT 的 `ver` 声明，校验时比对，不一致即失效。
- `credit_score` 冗余在用户表上，避免每次预约都去聚合信用流水；流水在 `credit_record` 里，两者由 Service 层保证一致。

### 3.2 lab — 实验室

| 字段 | 类型 | 允许空 | 默认值 | 说明 |
|------|------|--------|--------|------|
| id | BIGINT | 否 | AUTO | 主键 |
| code | VARCHAR(30) | 否 | - | 实验室编号，如 LAB-A301，唯一 |
| name | VARCHAR(100) | 否 | - | 实验室名称 |
| building | VARCHAR(50) | 是 | - | 所在楼栋 |
| room | VARCHAR(30) | 是 | - | 房间号 |
| capacity | INT | 是 | - | 可容纳人数 |
| open_time | TIME | 是 | - | 开放开始时间 |
| close_time | TIME | 是 | - | 开放结束时间 |
| need_approval | TINYINT | 否 | 1 | 是否需要审批 1 是 / 0 否 |
| manager_id | BIGINT | 是 | - | 负责人（sys_user.id） |
| status | TINYINT | 否 | 1 | 1 开放 / 0 停用 |
| description | VARCHAR(500) | 是 | - | 简介 |
| create_time | DATETIME | 是 | - | 创建时间 |
| update_time | DATETIME | 是 | - | 更新时间 |

**索引**：`uk_lab_code(code)`、`idx_building(building)`

**设计要点**
- `need_approval` 支持两种流程：需审批（提交后 PENDING）和免审批（提交即 APPROVED）。不同实验室可以有不同策略，比如公共机房免审批、贵重仪器室需审批。
- `open_time` / `close_time` 用 `TIME` 而非字符串，前端可直接用于生成时段选项，后端也能直接比较。
- `manager_id` 逻辑关联用户，不建外键；列表查询时组装 `managerName`。

### 3.3 equipment — 设备台账

| 字段 | 类型 | 允许空 | 默认值 | 说明 |
|------|------|--------|--------|------|
| id | BIGINT | 否 | AUTO | 主键 |
| code | VARCHAR(40) | 否 | - | 资产编号（对应设备铭牌），唯一 |
| name | VARCHAR(100) | 否 | - | 设备名称 |
| category | VARCHAR(50) | 是 | - | 类别：仪器仪表 / 计算设备 / 实验装置 |
| lab_id | BIGINT | 是 | - | 所属实验室 |
| model | VARCHAR(80) | 是 | - | 规格型号 |
| brand | VARCHAR(50) | 是 | - | 品牌 |
| purchase_date | DATE | 是 | - | 购置日期 |
| price | DECIMAL(12,2) | 是 | - | 设备价值（元） |
| status | VARCHAR(20) | 否 | IDLE | IDLE / IN_USE / REPAIR / SCRAPPED |
| keeper | VARCHAR(50) | 是 | - | 保管人 |
| description | VARCHAR(500) | 是 | - | 备注 |
| create_time | DATETIME | 是 | - | 创建时间 |
| update_time | DATETIME | 是 | - | 更新时间 |

**索引**：`uk_equipment_code(code)`、`idx_lab(lab_id)`、`idx_status(status)`

**设计要点**
- `code` 唯一且对应铭牌，报修时允许用户直接填资产编号定位设备（比下拉选择更快）。
- `status` 与报修联动：报修提交时设备置 `REPAIR`，验收完成后恢复 `IDLE`；`SCRAPPED` 设备禁止报修。
- `price` 用 `DECIMAL` 而非 `DOUBLE`，金额不能有浮点误差。

### 3.4 reservation — 实验室预约

| 字段 | 类型 | 允许空 | 默认值 | 说明 |
|------|------|--------|--------|------|
| id | BIGINT | 否 | AUTO | 主键 |
| order_no | VARCHAR(40) | 否 | - | 预约单号，唯一（RS + 时间戳 + 6 位随机） |
| user_id | BIGINT | 否 | - | 预约人 |
| lab_id | BIGINT | 否 | - | 实验室 |
| start_time | DATETIME | 否 | - | 开始时间 |
| end_time | DATETIME | 否 | - | 结束时间 |
| headcount | INT | 是 | - | 使用人数 |
| purpose | VARCHAR(200) | 是 | - | 使用用途 |
| remark | VARCHAR(500) | 是 | - | 备注 |
| status | VARCHAR(20) | 否 | PENDING | PENDING / APPROVED / REJECTED / CANCELLED / FINISHED |
| approver_id | BIGINT | 是 | - | 审批人 |
| approve_time | DATETIME | 是 | - | 审批时间 |
| approve_remark | VARCHAR(500) | 是 | - | 审批意见 |
| checkin_time | DATETIME | 是 | - | 签到时间 |
| checkin_status | VARCHAR(20) | 否 | NONE | NONE / CHECKED_IN / NO_SHOW |
| create_time | DATETIME | 是 | - | 创建时间 |
| update_time | DATETIME | 是 | - | 更新时间 |

**索引**：`uk_order_no(order_no)`、`idx_lab_time(lab_id, start_time, end_time)`、`idx_user(user_id)`、`idx_status(status)`、`idx_checkin(checkin_status, end_time)`

**设计要点**
- `idx_lab_time` 是冲突查询的核心索引：`WHERE lab_id = ? AND start_time < ? AND end_time > ?` 走这个联合索引，不用全表扫描。
- `idx_checkin(checkin_status, end_time)` 服务于爽约扫描：定时任务查 `checkin_status = 'NONE' AND end_time < now - 15min`。
- 单号带 6 位随机后缀，高并发下降低撞唯一索引的概率。
- `status` 与 `checkin_status` 分离：前者是审批流，后者是到场行为，两个维度不能混在一个字段里。

### 3.7 credit_record — 信用分变动明细

| 字段 | 类型 | 允许空 | 说明 |
|------|------|--------|------|
| id | BIGINT | 否 | 主键 |
| user_id | BIGINT | 否 | 用户 |
| event_key | VARCHAR(80) | 否 | 幂等键，唯一（如 `NO_SHOW:预约ID`） |
| event_type | VARCHAR(20) | 否 | 事件类型：NO_SHOW / CHECKIN / ADJUST / APPEAL |
| change_amount | INT | 否 | 变动值（正加负减） |
| score_before | INT | 否 | 变动前分数 |
| score_after | INT | 否 | 变动后分数 |
| reason | VARCHAR(300) | 否 | 变动原因 |
| operator_id | BIGINT | 是 | 操作人（系统自动为空） |
| create_time | DATETIME | 否 | 变动时间 |

**索引**：`uk_credit_event(event_key)`、`idx_credit_user(user_id, id)`

**设计要点**
- `event_key` 唯一索引实现**幂等**：同一次爽约无论重试多少次，只会扣一次分。这是防止重复扣分的关键设计。
- 同时记录 `score_before` 和 `score_after`，审计时可完整还原分数变化轨迹，不需要按时间倒推。

### 3.11 lab_closure — 闭馆安排

| 字段 | 类型 | 允许空 | 说明 |
|------|------|--------|------|
| id | BIGINT | 否 | 主键 |
| lab_id | BIGINT | 是 | 实验室 ID，**NULL 表示全校闭馆** |
| closure_date | DATE | 否 | 闭馆日期 |
| reason | VARCHAR(200) | 是 | 闭馆原因 |
| create_by | BIGINT | 是 | 创建人 |
| create_time | DATETIME | 是 | 创建时间 |

**索引**：`uk_lab_date(lab_id, closure_date)`、`idx_date(closure_date)`

**设计要点（踩过的坑）**
- `lab_id` 允许为空，表达「全校闭馆」这一特殊语义，避免为每个实验室插一条记录。
- 判重时必须用 `isNull()` 而不是 `eq(lab_id, null)`。后者生成 `lab_id = NULL`，SQL 三值逻辑下永远不成立，会导致同一天可以反复新增全校闭馆。这个缺陷已记录在测试报告中（BUG-001）。
- 唯一索引 `uk_lab_date(lab_id, closure_date)` 在 MySQL 中多个 NULL 不算重复，所以数据库层挡不住全校闭馆重复，必须靠应用层的 `isNull` 校验。

### 3.12 sys_log — 操作审计日志

| 字段 | 类型 | 允许空 | 默认值 | 说明 |
|------|------|--------|--------|------|
| id | BIGINT | 否 | AUTO | 主键 |
| operator_id | BIGINT | 是 | - | 操作人 ID |
| operator_name | VARCHAR(50) | 是 | - | 操作人姓名（冗余） |
| module | VARCHAR(40) | 是 | - | 业务模块 |
| action | VARCHAR(100) | 是 | - | 操作描述 |
| method | VARCHAR(200) | 是 | - | 调用方法 |
| uri | VARCHAR(200) | 是 | - | 请求路径 |
| ip | VARCHAR(50) | 是 | - | 来源 IP |
| params | VARCHAR(1000) | 是 | - | 参数摘要（脱敏） |
| success | TINYINT | 否 | 1 | 1 成功 / 0 失败 |
| error_msg | VARCHAR(500) | 是 | - | 失败原因 |
| cost_ms | BIGINT | 是 | - | 耗时（毫秒） |
| create_time | DATETIME | 是 | - | 操作时间 |

**索引**：`idx_operator(operator_id)`、`idx_create(create_time)`

**设计要点**
- `params` 长度限制 1000 并做脱敏，避免把密码等敏感信息写进日志。
- `success` + `error_msg` 记录失败操作，排查问题时能区分「没做」和「做了但失败」。
- `cost_ms` 可用于发现慢接口。

## 四、索引设计汇总

## 五、数据字典：枚举值

### 用户角色 `sys_user.role`
