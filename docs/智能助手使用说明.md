# 实验室智能助手使用说明

实现日期：2026-11-17。本文描述实际代码；早期《AI-Agent接入方案》中的排期和估算仅供历史参考。

## 能力和边界

- 登录后所有业务页面右下角有“智能助手”，支持真正的模型流式回复、工具轨迹、多轮上下文和确认卡片。
- 查询可预约实验室、推荐时段、查询本人预约、取消本人预约、查询设备、提交报修、查询本人报修（维修员查询指派工单）、看板问答。
- 管理员/教师可查询已有全局统计，学生/维修员只能查询个人统计。工单工具不提供任意 scope、用户ID或SQL入口。
- 写操作先生成卡片，用户点击“确认执行”后才调用原业务Service。文字“确认”不触发写入。取消工具仅允许取消本人的预约，包括管理员使用助手时。
- 预约卡片生成与提交都检查业务规则；最终提交保留原有事务、实验室行锁、信用限制、闭馆和冲突校验。补齐创建预约容量校验、精确8小时时长上限和禁止跨日。
- 排期为受限规则推荐：未来30天、08:00–20:00、每30分钟尝试一次、单次30–480分钟、最多20间候选实验室、最多3个结果，优先较早时段和容量适配。设备关键字只匹配空闲设备的名称/类别；不是全局最优算法。
- 数据问答只覆盖现有看板指标；没有新增任意历史日期报表、知识库、自动审批或自动派单。

## 模型与费用

默认DeepSeek官方服务（OpenAI兼容Chat Completions协议）：

```text
LLM_BASE_URL=https://api.deepseek.com
LLM_MODEL=deepseek-flash
LLM_API_KEY=在本地填写
```

模型API按输入/输出Token用量收费，工具往返也增加输入Token；规则演示不调用模型、不产生模型费用。余额不足、密钥错误、网络超时会在面板显示原因并降级；不会自动充值。费用以官方 https://api-docs.deepseek.com/quick_start/pricing/ 为准。

密钥只由后端读取，不使用 `VITE_` 环境变量，不写入前端、源码或聊天截图。已公开过的Key建议在平台轮换。

## 本地启动

PowerShell中先安全输入密钥，再在**同一窗口**启动后端（JDK21）：

```powershell
$agentSecret = Read-Host '输入模型API Key（隐藏输入）' -AsSecureString
$env:LLM_API_KEY = [System.Net.NetworkCredential]::new('', $agentSecret).Password
$env:MYSQL_PASSWORD = '你的本地数据库密码'
Set-Location lab-backend
mvn test
mvn package '-DskipTests'
java -jar target/lab-backend.jar
```

另开一个窗口，在 `lab-frontend` 执行 `npm run dev`，访问 http://localhost:5173 。

不配Key即可演示规则模式。勾选“使用规则演示”可强制不调用付费模型。修改配置后需要重启后端。后端已通过Spring配置导入读取当前目录或上一级的 `.env`；在项目根目录或 `lab-backend` 启动均可。环境变量优先于 `.env`，请清除之前设置的错误密码或占位符。

Docker Compose则把 `.env.example` 复制成 `.env`，本地填写 `LLM_API_KEY` 后执行 `docker compose up -d --build`。Compose已传递模型配置，Nginx已关闭聊天接口的响应缓冲。`.env` 已在Git忽略列表。

Windows启动脚本依赖已打包jar；更新代码后需重新打包。脚本已移除会覆盖真实密码的占位符，默认从本地 `.env` 读取配置；不要把密码或Key硬编码进bat文件。

## 演示指令

有余额的模型模式支持自由中文、多轮补充条件。规则模式仅识别受限格式，不具备完整自然语言推理，也不会从上一句猜测缺少字段：

```text
我的预约
预约 明天 14:00-16:00 4人 用途：数据库实验
预约 明天 14:00-16:00 4人 实验室：数据库 用途：数据库实验
查空闲 明天 14:00-16:00 4人
推荐 明天 4人 120分钟
取消预约 42
查设备 显微镜
报修 3 灯不亮还有糊味
我的报修
数据统计
```

预约/设备ID必须取自真实查询结果。规则模式预约会选取本次候选中容量适配的一间实验室，卡片中显示明确实验室；用户核对后再提交。有危险征兆的报修会标记紧急，并提示停止使用、联系负责人。

## 接口与运行约束

全部沿用JWT鉴权，未登录不可访问：

| 接口 | 用途 |
| --- | --- |
| `GET /api/agent/status` | 只返回配置状态、模型名，不返回Key，也不代表余额检查通过 |
| `POST /api/agent/chat` | JSON `{sessionId, message, ruleMode}`，返回SSE流 |
| `POST /api/agent/confirm` | JSON `{sessionId, actionId}`，只能执行服务端保存的卡片参数 |
| `DELETE /api/agent/sessions/{id}` | 清理本人会话 |

SSE事件：`session`、`mode`、`status`、`delta`、`tool`、`action`、`reset`、`error`、`done`。前端使用fetch携带Bearer Token并解析流。

会话归属固定用户，最多6轮上下文、每用户5个会话、全局500会话，空闲30分钟失效；卡片10分钟有效，最多8张待确认卡片。每会话间隔至少1.5秒，仅允许一轮在途请求；执行器最多4线程、等待队列16。模型最多4轮工具反馈、12次工具调用，单次请求最大1800输出Token。单条用户消息上限2000字符。

卡片参数保存在服务端，确认时不接受客户端重写业务参数。并发确认串行处理；同一卡片成功后重复点击返回已保存结果。失败或不确定结果的卡片也不会自动重放，应先到业务页面核对，再重新生成卡片。确认接口记录审计日志（会话与操作ID），不记录完整对话。

会话和确认状态仅存本进程内存，不适用于多副本部署。服务重启后旧卡片全部失效，需重建对话；同一真实请求经多个不同卡片确认仍可能被用户再次提交，业务冲突/重复报修规则负责最终拦截。规则模式和模型模式在UI明确区分，不能把规则回复当作模型联调成功。

## 信用与设备编号增补

目前工具共10个，新增 `query_my_credit`，可查询本人分数、预约资格、规则与最近10条明细。规则模式输入“我的信用分”同样可查。

个人中心提供“信用与预约资格”页，低于60分可提交10–500字的恢复申请。管理员在用户管理中审核，通过后至少恢复到70分；7天内最多通过一次，同时只允许一个待审申请。拒绝或通过都需要审核说明，审批后推送消息。近7天爽约限制独立于分数，页面显示预计解除时间。

新表 `credit_record`、`credit_appeal`使数据库增至12张业务表。历史分数保留，旧变动不补造流水，新的奖励、惩罚、恢复与人工调整均记账。修复签到后改期或取消、并发重复扣分、分数封顶时通知不准确的问题。

报修支持 `equipmentCode`。同时传 `equipmentId` 时必须一致；普通设备页面已自动传入两者。设备锁后的维修状态判断避免资产编号查询建立旧快照而引起重复报修。已完成20项新增真实MySQL联调和34项业务回归。
