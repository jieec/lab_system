# 答辩常见问题与参考回答

> 按「技术类 / 业务类 / 设计取舍类 / 挑刺类 / 团队类」五类整理。
> 回答原则：**先给结论，再给理由，最后给证据（代码/表/测试）**。不会的不要硬编。

## 一、技术类

### Q1：为什么选 Spring Boot 3 + Vue 3，而不是别的组合？

A：三个原因。第一，团队之前学过 Java 和 Vue，选熟悉的技术栈能把时间花在业务上而不是踩框架的坑。第二，Spring Boot 内嵌容器，`mvn spring-boot:run` 一条命令就能跑，答辩现场不会因为部署失败卡住。第三，Vue 3 配 Element Plus，管理后台需要的表格、表单、弹窗、时间轴组件都有现成的，不需要自己造。

如果重做，后端可能会考虑 Spring Boot + JPA 或者 Go，但就这个课程项目的规模和交付周期，当前选型是合适的。

### Q2：JWT 是无状态的，用户改密码后旧 token 怎么失效？

A：这是我们专门解决的一个问题。纯 JWT 确实没法主动撤回，所以我们加了**令牌版本号**机制：

- `sys_user` 表有 `token_version` 字段，签发 token 时把它写进 JWT 的 `ver` 声明。
- 每次请求，过滤器解析 token 后拿 `ver` 和数据库里的 `token_version` 比对，不一致就判定失效。
- 改密码、重置密码、停用账号时，`token_version` 自增，之前签发的所有 token 立刻全部失效。

代价是每个请求多查一次用户表。当前规模完全可接受，如果要优化，把版本号缓存在 Redis 就行。

### Q3：预约冲突是怎么判定的？两个用户同时约同一时段会怎样？

A：分两层。

**判定层**：用半开区间 `[start, end)` 判断相交，条件是 `s1 < e2 && e1 > s2`。用严格不等号的好处是「上一场 10 点结束、下一场 10 点开始」不算冲突，边界是准的。这个规则抽在 `TimeWindow` 类里，只有一处实现。

**并发层**：这是关键。如果只是「先查冲突再插入」，两个事务可能都查到没冲突、都插入成功。所以我们让所有写预约的事务**第一条语句就是 `SELECT ... FOR UPDATE` 锁实验室行**，把同一实验室的写操作串行化。等待锁的事务拿到锁之后才建立读视图，能看到前一个事务已提交的预约，从根本上消除 check-then-act 竞态。

另外预约单号加了 6 位随机后缀，防止高并发下单号撞唯一索引。

### Q4：为什么用 MyBatis-Plus 而不是 JPA？

A：主要是可控性。MyBatis-Plus 单表 CRUD 不用写 SQL，复杂查询还是可以写 XML 或手写 SQL，出了性能问题能直接看到执行的是什么语句。JPA 的自动生成 SQL 有时候不好预测，调优要跟框架斗。而且我们这个项目里有几处需要显式加锁（`FOR UPDATE`），MyBatis 写起来更直接。

### Q5：接口文档怎么维护的？会不会代码改了文档没改？

A：用 Knife4j（OpenAPI 3）从注解自动生成，不是手写文档。Controller 上标 `@Tag`，方法上标 `@Operation`，启动后访问 `/doc.html` 就能看到，还能直接在线调试。代码改了文档自动跟着变，不存在文档过期的问题。

另外我们额外整理了一份 `docs/接口文档.md`，按五个成员的分工组织，写清了每个接口的权限、参数、请求体、响应示例和枚举值，方便交接和答辩讲解。

### Q6：数据库为什么不用物理外键？

A：两个考虑。一是物理外键在删除时会级联或阻塞，业务上我们更希望用逻辑校验控制（比如删实验室前先检查有没有未完成预约），而不是让数据库直接抛错。二是分库分表或者数据迁移时物理外键会很麻烦。所以关联关系在 Service 层保证，表结构只建索引。

### Q7：系统的安全性做了什么？

A：五个方面。

1. 密码用 BCrypt 加密存储，不是 MD5，自带盐值，抗彩虹表。
2. 密码字段加 `@JsonIgnore`，接口永远不会把密码返回给前端。
3. JWT 签名 + 过期时间 + 令牌版本号，支持主动失效。
4. 接口级角色校验，`@RequireRole` 注解声明，不在业务代码里散落 if 判断。
5. 敏感操作通过 `@OperationLog` 切面自动落审计日志，记录操作人、IP、参数、耗时。

还有一点：仓库里的配置文件用占位符，真实数据库密码不提交到 Git。

## 二、业务类

### Q8：信用分机制的规则是什么？为什么这么设计？

A：初始 100 分，范围 0–100。

- 爽约扣 10 分：预约结束后 15 分钟仍未签到，系统判爽约。
- 签到加 2 分：鼓励按时到场，满分不叠加。
- 低于 60 分禁止预约：连续 5 次爽约就会跌破门槛。
- 近 7 天爽约 3 次及以上也暂停预约：防止有人分数还没跌破但行为已经很差。
- 可以申请恢复：管理员审核通过后至少恢复到 70 分，7 天内最多通过一次，避免变成「无限复活」。

为什么这么设计：单纯封号太重，单纯警告太轻。用分数做渐进式约束，既给了改正机会，又让屡次爽约的人真的约不到，比人工审批更公平也可执行。所有变动都有 `credit_record` 流水，可追溯、可申诉。

### Q9：签到窗口为什么是开始前 15 分钟？爽约判定为什么是结束后 15 分钟？

A：15 分钟是个经验值，兼顾两头：

- 太早开放签到，学生可能上午就把晚上的签了，签到就失去意义。
- 太晚开放，学生提前到了站在门口签不了，体验差。
- 爽约判定留 15 分钟缓冲，是考虑下课拖堂、路上耽误这种合理延迟。

这两个值是常量，写在 `ReservationService` 里，要调整改一处就行。

### Q10：报修流程为什么要经过管理员派单，不能直接推给维修员？

A：因为维修员有分工（电器、网络、机械），而且需要优先级排序。如果报修直接广播给所有维修员，会出现两个问题：一是没人认领或者多人抢单，二是紧急的工单被淹没。

管理员派单相当于一个调度台，可以根据故障类型、紧急程度、维修员当前负载来分配。派单后维修员在「我的工单」里只看到分配给自己的，职责清晰。

### Q11：闭馆安排为什么 `lab_id` 允许为空？

A：为了支持两种粒度：`lab_id` 有值表示某个实验室单独闭馆（比如设备检修），为空表示全校闭馆（比如法定节假日）。前端展示时，为空的显示「全校」。

这里踩过一个坑：判断「某天是否已有全校闭馆」时，如果用 `eq(lab_id, null)`，SQL 三值逻辑下 `lab_id = NULL` 永远不成立，会导致同一天可以反复新增全校闭馆。必须用 `isNull()`。这个我们已经在代码里修正并注释了原因。

### Q12：站内信是什么时候触发的？

A：目前是业务动作触发。预约审批通过/驳回、报修派单/完成、信用分变动，都会往 `message` 表插一条记录，带 `type`（预约/报修/信用/系统）和 `biz_id`（关联业务单据），前端顶部显示未读数角标，点进去能跳到对应详情。

没有做实时推送（WebSocket），用的是轮询未读数，因为课程项目规模下轮询够用，实现成本低很多。

## 三、设计取舍类

### Q13：为什么用 SSE 而不是 WebSocket 做 AI 对话？

A：AI 对话是**单向流式输出**——用户发一次请求，服务端持续推字，不需要双向实时通信。SSE 基于普通 HTTP，实现简单，不需要额外协议升级和心跳维护，Nginx 配一下 `X-Accel-Buffering: no` 就能正常流式。WebSocket 适合聊天室这种双向高频场景，用在这里是过度设计。

### Q14：AI 助手为什么要加「确认卡片」？

A：因为它是能真正操作数据库的，不是只会聊天。如果用户说「帮我约明天下午两点」，助手直接调用接口创建预约，一旦理解错了（时间理解错、实验室选错），就是脏数据。

所以我们把工具分成两类：**读操作**直接执行（查实验室、查时段），**写操作**必须先返回待确认动作，前端弹卡片显示「将要执行什么、参数是什么」，用户点确认才真正落库。这是 AI 系统里「human in the loop」的常规做法。

### Q15：为什么把信用规则、状态机、时段判定抽成独立的类？

A：三个好处。

1. **单一实现**：规则只写一遍，不会出现 Service A 和 Service B 判断不一致。
2. **可测试**：这些类不依赖数据库和 Spring 容器，测试直接 new 出来断言，跑得快。我们的测试用例里有 30 多个是直接测这三个类的。
3. **易修改**：要调信用门槛，改 `CreditPolicy.FLOOR` 一个常量，全系统生效。

### Q16：前端状态管理为什么用 Pinia？

A：Vue 3 的官方推荐，比 Vuex 更轻，没有 mutations 那层样板代码，组合式写法更自然。我们只存了登录用户信息和少量全局状态，不需要复杂的状态管理方案。

## 四、挑刺类（老师最爱问）

### Q17：这个系统看起来就是个 CRUD，创新点在哪？

A：（不要慌，先承认再区分）基础管理功能确实是 CRUD，这部分任何系统都躲不掉。但我们有三个不是 CRUD 的地方：

1. **并发安全的预约**：不是简单插入，是用行锁 + 当前读解决 check-then-act 竞态，这是有并发正确性要求的。
2. **信用分机制**：把「爽约」这个行为量化成可执行的约束，带流水、带申诉、带恢复上限，是一套完整的行为治理设计，不是加个字段。
3. **AI 助手真正能办事**：不是套壳聊天，是 Function Calling 调真实接口，并且用确认卡片解决 AI 误操作的风险。

如果只做 CRUD，答辩十分钟就讲完了；我们花了最多时间的是并发和规则设计。

### Q18：如果用户量涨到一万，这套系统撑得住吗？

A：现在的瓶颈点有三个，都能改：

1. **预约行锁**：现在是数据库行锁，同一实验室串行。量大了换成 Redis 分布式锁，或者按实验室分片，不同实验室互不影响。
2. **token 版本号每次查库**：加 Redis 缓存，失效时删缓存。
3. **列表查询**：给常用筛选字段建联合索引，热点数据加缓存。

数据库层面单表万级数据 MySQL 完全没压力，真正的瓶颈会先出现在 AI 助手的 LLM 调用上（有延迟和配额），那块可以加队列和缓存常见问答。

### Q19：为什么没有做单元测试覆盖所有 Service？

A：Service 层依赖数据库和 Spring 容器，写集成测试成本高、跑得慢。我们的策略是把**最容易出错的纯逻辑**抽出来做单元测试——信用规则、状态机、时段冲突、JWT、响应结构，这部分有 70 多个用例，覆盖了边界值和异常路径。涉及数据库的流程用集成测试和手工验证结合。

这个取舍是明确的：把测试预算花在规则复杂度最高的地方，而不是追求覆盖率数字。

### Q20：演示时如果系统崩了怎么办？

A：（这是压力测试，稳住）我们有兜底：一是提前准备了关键页面截图和一段录屏，服务异常时用截图讲；二是接口文档是独立的，打开 `/doc.html` 可以单独演示接口；三是数据可以重新导入 `schema.sql` + `data.sql` 恢复。启动脚本也是一键的，重启大概 30 秒。

### Q21：这个项目的代码量大概多少？你们五个人怎么分工的？

A：后端 13 个 Controller、12 个实体、业务层按模块拆分，前端页面按角色划分，数据库 12 张表。分工是按业务域纵向切的，每个人负责从接口到页面的完整一条线，避免前后端互相等待：

| 成员 | 负责模块 |
|------|----------|
| A | 登录认证、用户管理、JWT 与权限体系 |
| B | 实验室管理、设备台账 |
| C | 实验室预约、闭馆安排、时段冲突 |
| D | 报修运维、信用管理 |
| E | 通知公告、站内信、审计日志、统计看板、AI 助手 |

公共部分（统一响应、异常处理、日志切面、规则类）由 A 和 E 牵头定规范，其他人按规范写。

### Q22：有没有考虑过用现成的开源实验室预约系统？

A：考虑过，但没用。原因有两个：一是现成系统的业务模型和我们学校不一致（比如没有信用分、没有报修闭环），改造成本可能比自己写还高；二是课程项目本身要体现设计能力，直接套开源系统答辩时讲不出东西。

不过我们参考了几个开源项目的表结构设计，特别是预约表和工单表的状态字段设计。

## 五、团队协作类

### Q23：五个人怎么保证代码风格一致？

A：三个约定：

1. **分层约定**：Controller 只做参数接收和返回，业务逻辑一律在 Service，不允许 Controller 里写业务。
2. **返回结构统一**：所有接口返回 `R<T>`，分页返回 `PageResult<T>`，不允许各写各的。
3. **规则集中**：涉及业务规则的判断抽成独立类，不允许在 Service 里散落魔法数字。

另外用 Git 分支管理，主分支只合可运行的代码。

### Q24：遇到最大的困难是什么？怎么解决的？

A：（选一个真实的讲，建议讲并发那个，最有技术含量）

最大的困难是预约的并发冲突。最初是「先查有没有冲突，没有就插入」，测试时两个请求同时发，发现都能成功，数据库里出现了重叠的两条预约。

排查后明白是 check-then-act 竞态：两个事务在各自的一致性读视图里都看不到对方未提交的数据。解决方案是把事务的第一条语句改成 `SELECT ... FOR UPDATE`，用当前读锁住实验室行，让同一实验室的写操作串行化。这样后到的事务必须等前一个提交后才能继续，拿到锁之后再查就能看到新数据了。

改完之后用并发脚本压测，重叠预约不再出现。

## 六、回答技巧

| 场景 | 做法 |
|------|------|
| 会的问题 | 结论先行 → 理由 → 证据（"代码在 X 类里" / "表里有个字段"） |
| 半会的问题 | 说清楚现在怎么做的，再补一句"如果要做可以这样扩展" |
| 完全不会 | "这块我们目前没做到，如果要做的话我的思路是……"——不要沉默，不要编 |
| 被质疑设计 | 先承认局限，再说当时的约束（时间、规模、团队），最后说改进方向 |
| 被追问细节 | 能说出具体类名、表名、字段名，可信度立刻不一样 |
| 时间不够 | "这个展开讲比较长，我一句话总结是……" |
