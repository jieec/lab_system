# 答辩现场演示脚本

> 建议时长：8–10 分钟。开场 1 分钟，功能演示 6 分钟，技术说明 2 分钟，收尾 1 分钟。
> 演示前 10 分钟务必完成「演示前检查清单」。

---

## 二、演示动线（按此顺序走，一条主线串起全部模块）

### 第 1 步｜开场与登录（40 秒）

**话术**：
> "我们做的是高校实验室预约与设备运维系统。核心解决三个痛点：预约靠微信群容易冲突、设备坏了报修没人跟、用完了不来也没人管。系统分四种角色：学生、教师、管理员、维修员。"

**操作**：用 `admin` 登录 → 停在首页看板。

**讲要点**：首页看板一次性展示实验室总数、设备总数、今日预约、待处理工单，是管理者进入系统的第一屏。

---

### 第 2 步｜实验室与设备台账（1 分钟）

**操作**：进入「实验室管理」→ 看到卡片式列表（含设备数、今日预约数）→ 点进任意实验室 → 展示开放时间、容纳人数、负责人、设备清单。

**话术**：
> "实验室按楼栋和关键词筛选，卡片上直接显示该实验室有多少台设备、今天有几个时段被占用。点进去能看到完整设备清单，每台设备有资产编号、型号、品牌、购入日期、当前状态。"

**接着**：进入「设备管理」→ 按类别筛选 → 演示修改设备状态为「维修中」。

**讲要点**：设备状态有四种：空闲 / 使用中 / 维修中 / 已报废，报废设备不能报修。

---

### 第 3 步｜预约全流程（2 分钟，核心亮点）

**操作**（学生窗口，用 `s2021001` 登录）：

1. 进入「实验室预约」→ 选实验室 → 打开时段选择，展示**时间轴**：已占用时段灰掉，不可选。
2. 选一个空闲时段 → 填写人数、用途 → 提交 → 提示「提交成功，等待审批」。

**话术**：
> "时段冲突是在后端判定的，用半开区间 `[start, end)` 判断相交：`s1 < e2 && e1 > s2`。这样「上一场 10 点结束、下一场 10 点开始」不算冲突，边界处理是准确的。"

**切换教师窗口**（`t_wang`）：

3. 进入「预约审批」→ 看到刚才的待审批单 → 点通过 → 填写备注。

**切回学生窗口**：

4. 刷新「我的预约」→ 状态变为「已通过」→ 点「签到」→ 提示签到成功。
5. 再点「申请改期」→ 选新时段 → 提交。

**讲要点**：
> "签到窗口是开始前 15 分钟开放。预约结束后 15 分钟还没签到，系统自动判爽约，扣 10 分信用分。签到一次加 2 分，满分 100 不叠加。"

---

### 第 4 步｜信用分机制（1 分钟，差异化亮点）

**操作**：用 `s2021030`（70 分 / 3 次爽约）登录 → 进入「我的信用」→ 展示分数、爽约记录、限制提示 → 尝试预约 → **被拦截**，提示「信用分不足或近期爽约次数过多」。

**话术**：
> "信用分是本系统区别于普通预约系统的设计。规则是：初始 100 分，爽约扣 10 分，签到加 2 分，低于 60 分禁止预约，近 7 天爽约 3 次及以上也暂停预约。被限制的学生可以提交信用恢复申请，管理员审核通过后至少恢复到 70 分。"

**接着**（管理员窗口）：进入「信用管理」→ 审核一条恢复申请。

**讲要点**：所有扣分、加分都有 `credit_record` 流水记录，可追溯，不是直接改数字。

---

### 第 5 步｜报修运维闭环（1.5 分钟）

**操作**：

1. 学生窗口 → 「设备报修」→ 选设备 → 填故障描述 → 提交 → 提示工单号。
2. 管理员窗口 → 「报修管理」→ 看到待派单工单 → 派单给 `r_zhang`。
3. 维修员窗口（`r_zhang`）→ 看到「我的工单」→ 点「开始维修」→ 填维修描述和费用 → 提交。
4. 学生窗口 → 「我的报修」→ 点「验收」→ 打分 5 分 → 完成。

**话术**：
> "报修是完整闭环：待派单 → 已派单 → 维修中 → 待验收 → 已完成。每一步都会写一条 `repair_log` 流转记录，谁在什么时间做了什么操作，全程留痕。系统还做了并发保护：同一台设备不允许同时存在两张未完成的工单，防止重复报修。"

---

### 第 6 步｜AI 智能助手（1 分钟，加分项）

**操作**：打开右下角助手 → 输入「今天 A301 实验室还有哪些空时段」→ 展示流式回答 → 再输入「帮我预约明天下午 2 点到 4 点」→ 弹出**确认卡片** → 点确认 → 预约创建成功。

**话术**：
> "助手用的是 SSE 流式对话加 Function Calling。它不是一个只会聊天的机器人，而是能真正调用系统接口办事。但涉及写操作——比如提交预约、提交报修——必须先弹确认卡片，用户点了确认才真正执行，避免 AI 误操作。"

---

### 第 7 步｜管理端与审计（1 分钟）

**操作**：管理员窗口依次展示：

- 「用户管理」：新增用户（提示初始密码 123456）、重置密码、停用账号。
- 「闭馆安排」：新增一个闭馆日期 → 回到预约页，该日期不可选。
- 「审计日志」：展示刚才所有操作的记录（模块、动作、操作人、IP、耗时、成功与否）。

**话术**：
> "所有敏感操作通过 `@OperationLog` 注解自动落库，不需要在每个接口里手写日志代码。管理员可以按模块和关键词查，出问题能定位到人和时间。"

---

### 第 8 步｜技术收尾（1 分钟）

**话术**：
> "技术栈是 Vue 3 + Spring Boot 3 + MySQL 8，前后端分离，MyBatis-Plus 做持久层。安全上密码用 BCrypt 加密，JWT 里带一个 token 版本号，改密码或者停用账号时版本号自增，之前签发的 token 立刻失效——这解决了 JWT 无法主动注销的老问题。接口文档用 Knife4j 自动生成，可以现场调试。数据库 12 张表，测试用例 70 多个，覆盖信用分、状态机、时段冲突这些核心规则。"

## 三、时间不够时的取舍（按优先级删）

如果只剩 5 分钟，按此顺序保留：

1. **预约全流程 + 时段冲突**（必讲，核心）
2. **信用分拦截**（差异化亮点）
3. **报修闭环**（业务完整度）
4. 管理端审计日志（一句话带过）
5. AI 助手（放最后，时间够就演示，不够就口头提一句）

## 四、演示失败兜底方案

| 故障 | 应对 |
|------|------|
| 后端启动失败 | 检查 MySQL 是否启动、`.env` 里 `MYSQL_PASSWORD` 是否正确；改用手头截图讲 |
| 前端白屏 | 检查 8080 是否通；直接打开 `http://localhost:8080/doc.html` 用接口文档演示 |
| 端口被占用 | 换端口启动：`--server.port=8081`，前端 `npm run dev -- --port 5174` |
| 数据被改乱 | 重新导入 `lab-backend/src/main/resources/sql/schema.sql` + `data.sql` |
| 投屏字太小 | 浏览器 `Ctrl +` 放大到 125%，或提前录一段 3 分钟演示视频 |
