## 一、测试范围与策略

### 1.1 测试分层

| 层次 | 内容 | 数量 | 是否依赖数据库 |
|------|------|------|----------------|
| 规则层测试 | 信用分、预约状态机、时段冲突、用户上下文、参数校验、JSON 序列化 | 121 | 否 |
| 服务层测试 | 预约、报修、信用、闭馆、认证（Mockito 模拟 Mapper） | 42 | 否 |
| 智能助手测试 | 会话、工具调用、LLM 客户端、规则兜底、HTTP 接口 | 29 | 否 |
| 综合场景测试 | 跨模块组合与边界场景 | 7 | 否 |

**全量测试不依赖数据库、不依赖 Spring 容器、不依赖外部 LLM 服务**，可在任意机器上 `mvn test` 直接跑通。

### 1.2 为什么这么分层

Service 层依赖数据库，写集成测试成本高、跑得慢、环境敏感。我们的策略是把**最容易出错的纯逻辑抽出来做单元测试**——规则、状态机、校验、序列化——这些地方一个符号写错就是生产事故，而 CRUD 的增删改查出错概率低且容易在联调时发现。

所以测试预算集中在规则复杂度最高的地方，而不是追求覆盖率数字好看。

## 四、缺陷记录

测试过程中发现并修复的 4 个缺陷，全部有对应回归用例。

| 编号 | 缺陷描述 | 严重级别 | 发现方式 | 修复方案 | 回归用例 |
|------|----------|----------|----------|----------|----------|
| BUG-001 | 全校闭馆重复新增：`eq(lab_id, null)` 生成 `lab_id = NULL`，SQL 三值逻辑下永不成立，同一天可反复插入全校闭馆 | 高 | 手工测试 | 改用 `isNull(LabClosure::getLabId)` | `LabClosureServiceTest` |
| BUG-002 | 并发预约重叠：先查冲突再插入存在 check-then-act 竞态，两个事务可同时成功 | 高 | 并发压测 | 事务首语句 `SELECT ... FOR UPDATE` 锁实验室行 | `ReservationServiceTest` 审批二次校验 |
| BUG-003 | 改密码后旧 token 仍有效：纯 JWT 无状态，服务端无法撤回 | 高 | 安全自查 | 引入 `token_version` + JWT `ver` 声明比对 | `AuthServiceTest`、`JwtUtilTest` |
| BUG-004 | 密码可能泄露到接口响应：`SysUser` 含 `password` 字段，若直接返回会带出 BCrypt 密文 | 中 | 代码评审 | 字段加 `@JsonIgnore`，并补序列化测试守住 | `PasswordSerializationTest` |

### 缺陷分布

| 模块 | 数量 | 说明 |
|------|------|------|
| 预约 | 1 | 并发竞态 |
| 闭馆 | 1 | SQL null 语义 |
| 认证安全 | 2 | token 失效、密码泄露 |

## 六、执行方式

```bash
cd lab-backend

# 全量测试
mvn test

# 只跑核心规则
mvn test -Dtest=SystemCoreTest

# 只跑某个模块
mvn test -Dtest=ReservationServiceTest

# 生成报告（surefire 报告在 target/surefire-reports/）
```

## 七、结论

1. 199 个用例全部通过，核心业务规则（信用分、状态机、时段冲突）与安全机制（JWT、密码保护）均有测试覆盖。
2. 全量测试不依赖数据库与外部服务，可在任何装有 JDK 21 + Maven 的机器上复现。
3. 测试过程中发现 4 个缺陷，其中 3 个为高严重级别，均已修复并补充回归用例。
4. 未覆盖部分为有意识的取舍，已说明替代验证方式。
