# 系统架构与技术方案说明

## 一、总体架构

系统采用**前后端分离**的 B/S 架构，分为表现层、接口层、业务层、持久层、数据层五层。

```
┌──────────────────────────────────────────────────────────┐
│  浏览器（Vue 3 SPA）                                      │
│  Element Plus 组件 / Pinia 状态 / Vue Router 路由          │
└───────────────────────────┬──────────────────────────────┘
                            │ HTTP + JSON（/api 前缀）
                            │ Vite 开发代理转发到 8080
┌───────────────────────────▼──────────────────────────────┐
│  Spring Boot 3 应用（端口 8080）                          │
│                                                          │
│  ┌────────────────────────────────────────────────────┐  │
│  │ 接口层 Controller（13 个，统一返回 R<T>）           │  │
│  └────────────────────────────────────────────────────┘  │
│  ┌────────────────────────────────────────────────────┐  │
│  │ 横切层：JWT 过滤器 / 角色校验 / 操作日志切面 / 异常  │  │
│  └────────────────────────────────────────────────────┘  │
│  ┌────────────────────────────────────────────────────┐  │
│  │ 业务层 Service（预约、报修、信用、闭馆、认证…）      │  │
│  └────────────────────────────────────────────────────┘  │
│  ┌────────────────────────────────────────────────────┐  │
│  │ 持久层 Mapper（MyBatis-Plus）                        │  │
│  └────────────────────────────────────────────────────┘  │
└───────────────────────────┬──────────────────────────────┘
                            │ JDBC
┌───────────────────────────▼──────────────────────────────┐
│  MySQL 8（12 张表）                                       │
└──────────────────────────────────────────────────────────┘
```

## 二、技术选型与理由

| 层次 | 选型 | 选型理由 |
|------|------|----------|
| 前端框架 | Vue 3（Composition API） | 学习成本低、生态成熟，组合式 API 便于按业务抽逻辑 |
| 构建工具 | Vite | 冷启动毫秒级，热更新快，开发体验明显优于 Webpack |
| UI 组件 | Element Plus | 表格、表单、弹窗、时间轴组件齐全，管理后台开箱即用 |
| 状态管理 | Pinia | 比 Vuex 更轻，TypeScript 友好，按模块拆分 store |
| 后端框架 | Spring Boot 3 | 自动装配、内嵌容器，一个 jar 即可运行；生态完整 |
| 持久层 | MyBatis-Plus | 单表 CRUD 零 SQL，复杂查询仍可写 XML，比 JPA 更可控 |
| 数据库 | MySQL 8 | 事务与行锁机制成熟，适合预约这类需要并发控制的场景 |
| 认证 | JWT（jjwt） | 无状态，适合前后端分离；配合 token 版本号解决注销问题 |
| 接口文档 | Knife4j / OpenAPI 3 | 注解自动生成，可在浏览器直接调试 |
| 构建 | Maven | 依赖管理规范，`mvn spring-boot:run` 即可启动 |

## 三、分层设计

### 3.1 接口层（Controller）

- 13 个 Controller，按业务域划分：认证、用户、实验室、设备、预约、闭馆、报修、信用、通知、站内信、日志、统计、AI 助手。
- 统一返回 `R<T>`：`{ code, msg, data }`，前端只需判断 `code`。
- 分页统一返回 `PageResult<T>`：`{ total, records }`。
- 参数校验用 Jakarta Validation 注解（`@NotNull`、`@NotBlank`、`@Min`），失败由全局异常处理器统一转成友好中文提示。
- 权限用自定义注解 `@RequireRole("ADMIN")` 声明式标注，不在业务代码里写 if 判断。

### 3.2 横切层

| 组件 | 作用 |
|------|------|
| `JwtFilter` | 解析 `Authorization: Bearer <token>`，校验签名与过期，比对 token 版本号，写入 `UserContext` |
| `UserContext` | 基于 `ThreadLocal` 保存当前登录用户，业务层直接 `UserContext.userId()` 取值 |
| `@RequireRole` + 拦截器 | 在进入 Controller 前校验角色，不匹配抛 403 |
| `@OperationLog` + AOP 切面 | 自动记录操作人、模块、动作、URI、IP、参数、耗时、成功与否，落 `sys_log` 表 |
| 全局异常处理器 | 捕获 `BizException` 转 `R.fail(code, msg)`；捕获参数校验异常转中文提示；兜底捕获未知异常 |

### 3.3 业务层（Service）

业务规则集中在 Service，且**把关键规则抽成独立的规则类**，避免逻辑散落：

| 规则类 | 职责 |
|--------|------|
| `TimeWindow` | 时段冲突判定的唯一定义处（半开区间相交） |
| `ReservationState` | 预约状态机，集中定义合法流转，非法流转抛异常 |
| `CreditPolicy` | 信用分规则唯一定义处（门槛、扣分、加分、上限） |

这样做的好处：规则只有一处实现，测试可以脱离数据库直接覆盖，改规则时不会漏改。

## 四、关键技术方案

### 4.1 预约并发安全（重点）

**问题**：两个用户同时预约同一实验室同一时段，如果先查冲突再插入，会出现「都查到没冲突、都插入成功」的竞态。

**方案**：所有会写预约记录的事务，**第一条语句就是当前读加锁**：

```sql
SELECT id FROM lab WHERE id = ? FOR UPDATE
```

先锁实验室行，把同一实验室的写操作串行化。等待锁的事务在拿到锁之后才建立一致性读视图，因此能看到前一个事务已提交的预约，从根本上消除 check-then-act 竞态。

**配合措施**：
- 预约单号加 6 位随机后缀，避免高并发下单号撞唯一索引。
- 冲突判定使用 `TimeWindow.overlaps`，语义统一。
- 信用分变动也先锁用户行（`selectByIdForUpdate`），保证同一用户不同预约的扣分不会互相覆盖。

### 4.2 JWT 主动失效

**问题**：JWT 是无状态的，签发后服务端无法撤回，改密码或停用账号后旧 token 仍然有效。

**方案**：`sys_user` 增加 `token_version` 字段，签发时写入 JWT 的 `ver` 声明。校验时比对数据库中的版本号，不一致即视为失效。改密码、重置密码、停用账号时版本号自增，之前所有 token 立即失效。

**代价**：每次请求需查一次用户表。当前规模下可接受；如需优化可加 Redis 缓存版本号。

### 4.3 报修工单闭环

状态流转：`PENDING`（待派单）→ `ASSIGNED`（已派单）→ `REPAIRING`（维修中）→ `DONE`（待验收）→ `VERIFIED`（已完成）。

**防重复报修**：提交报修时先锁设备行（`selectByIdForUpdate`），再检查是否存在未完成工单，避免同一台设备出现两张并行工单。已报废设备直接拒绝报修。

**全程留痕**：每次流转写一条 `repair_log`，记录操作人、动作、内容，前端按时间轴展示。

### 4.4 信用分机制

| 规则 | 数值 |
|------|------|
| 初始分 | 100 |
| 分数范围 | 0–100 |
| 爽约扣分 | −10 |
| 签到加分 | +2（满分不叠加） |
| 预约门槛 | ≥ 60 |
| 近期限制 | 近 7 天爽约 ≥ 3 次暂停预约 |
| 恢复申请 | 管理员通过后至少恢复至 70，7 天内最多通过一次 |

所有变动写 `credit_record` 流水（事件类型、变动值、变动前后分数、原因、操作人），可追溯。用 `event_key` 做幂等，同一次爽约不会重复扣分。

### 4.5 闭馆与时段可用性

- `lab_closure` 表记录闭馆日期，`lab_id` 为空表示全校闭馆。
- 新增闭馆时用 `isNull()` 而非 `eq(column, null)`——后者在 SQL 三值逻辑下永远不成立，会导致同一天可反复新增全校闭馆。
- 预约提交时先校验目标日期是否闭馆，闭馆日期直接拒绝。

### 4.6 AI 智能助手

- **通信**：SSE（Server-Sent Events）流式返回，用户看到逐字输出而非长时间等待。
- **能力**：Function Calling，助手可调用系统业务工具（查实验室、查时段、提交预约、提交报修等）。
- **安全**：写操作必须经过「确认卡片」——助手返回待确认动作，前端弹卡片，用户点击后调用 `/api/agent/confirm` 才真正执行。
- **降级**：LLM 不可用时走规则兜底（关键词匹配），保证功能不整体瘫痪。

## 五、数据库设计

12 张表，分为四组：

| 分组 | 表 |
|------|-----|
| 用户与权限 | `sys_user` |
| 资源 | `lab`、`equipment`、`lab_closure` |
| 业务 | `reservation`、`repair_order`、`repair_log`、`credit_record`、`credit_appeal` |
| 支撑 | `notice`、`message`、`sys_log` |

核心关系：

```
sys_user 1 ──< reservation >── 1 lab
sys_user 1 ──< repair_order >── 1 equipment >── 1 lab
repair_order 1 ──< repair_log
sys_user 1 ──< credit_record
sys_user 1 ──< message
```

设计要点：
- 外键逻辑关联但不建物理外键，避免级联删除风险，关联查询在 Service 层组装。
- 列表接口需要的冗余字段（如 `labName`、`equipmentName`）用 `@TableField(exist = false)` 承载，不落库。
- 时间字段统一 `LocalDateTime` / `LocalDate` / `LocalTime`，避免时区歧义。

## 六、代码结构

```
lab-backend/
└── src/main/java/com/lab/system/
    ├── common/        R、PageResult、BizException、规则类
    ├── config/        MyBatis-Plus、跨域、Knife4j 配置
    ├── controller/    13 个接口控制器
    ├── dto/           请求参数对象（含校验注解）
    ├── entity/        12 个实体，与表一一对应
    ├── mapper/        MyBatis-Plus Mapper
    ├── security/      JWT、UserContext、权限注解、日志切面
    ├── service/       业务逻辑
    └── agent/         AI 助手（会话、工具、LLM 客户端）

lab-frontend/
└── src/
    ├── api/           接口封装
    ├── views/         页面
    ├── components/    公共组件
    ├── router/        路由与权限守卫
    └── stores/        Pinia 状态
```

## 七、可扩展性

| 扩展方向 | 现有设计如何支撑 |
|----------|------------------|
| 多校区 | `lab` 增加 `campus_id`，预约查询加校区过滤即可 |
| 消息推送 | `message` 表已存在，接入短信/邮件只需在 Service 加一个发送器 |
| 权限细化 | `@RequireRole` 可扩展为 `@RequirePermission`，角色与权限解耦 |
| 高并发 | 预约锁可从行锁升级为 Redis 分布式锁；token 版本号可缓存到 Redis |
| 数据报表 | `sys_log`、`reservation` 已有完整数据，可直接接 BI 或导出 Excel |
